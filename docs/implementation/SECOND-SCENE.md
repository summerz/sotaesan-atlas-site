# 두 번째 장면: Sunnyvale Museum 벽 비교

## 목적과 출처

기존 Knock Hall 한 장면에서만 관찰한 벽 근접 비침을 다른 촬영 데이터로 확인한다. 새 장면은 **Sunnyvale Heritage Park Museum**, 제작자는 **Damjan Cvetkov Dimitrov (zeitgeistarchivescans)**다.

- [장면 원본과 제작자](https://superspl.at/scene/d5d397aa)
- [PlayCanvas 공식 1인칭 보행 예제](https://github.com/playcanvas/engine/blob/main/examples/src/examples/gaussian-splatting/first-person.example.mjs)
- [배포 SOG](https://code.playcanvas.com/examples_data/example_sunnyvale/sunnyvale.sog)
- [함께 배포된 충돌 GLB](https://code.playcanvas.com/examples_data/example_sunnyvale/sunnyvale.glb)

SOG 내부 `license.txt`는 제작자 표시를 요구하는 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)을 명시한다. 위 제작자와 출처를 기록한다.

## 실행과 확인

현재 실행 중인 서버에서 다음 주소를 연다. 상단 `장면` 메뉴로도 선택할 수 있다. 장면을 바꾸면 페이지가 다시 로드된다.

- Three.js: <http://127.0.0.1:5173/?scene=sunnyvale>
- PlayCanvas: <http://127.0.0.1:5174/?scene=sunnyvale>
- 기존 장면: 각 주소의 `?scene=hall` 또는 쿼리가 없는 기본 주소

서버가 종료된 경우 `./dev.sh --preview both`로 실행한다. 코드 변경 후 다시 실행할 때는 `pnpm build:spikes`로 빌드한다.

같은 창 크기로 한 앱씩 확인한다. 이번에는 기존 비교 경로와 JSON 측정을 반복할 필요가 없다.

1. 로드가 끝나면 벽을 멀리서 바라본다. 처음부터 구멍이나 배경 비침이 있는지 확인한다.
2. 벽에 가까이 걸어가 충돌로 멈추는 지점에서 확인한다. 접근하면서 비침이 생기는지, 벽을 통과하는지 구분한다.
3. 그 상태에서 옆으로 이동하고 시선을 돌린다. 비침이 벽의 같은 위치에 남는지, 시선에 따라 바뀌는지 확인한다.
4. 다른 앱에서 같은 벽과 비슷한 위치를 확인한다. `R` 또는 `시작점으로`로 복귀할 수 있다.

비침이 보이면 장면·벽 위치·거리·충돌 여부를 적고 화면을 남긴다. 수동 이동은 정확히 같은 카메라 위치를 보장하지 않으므로 스크린샷 차이만으로 엔진 문제를 확정하지 않는다.

### 충돌 면과 문제 위치 기록

두 앱에 `충돌 면 보기`와 `위치 JSON 저장`을 추가했다. `Esc`로 마우스를 해제하고 버튼을 누른다.

- `충돌 면 보기`: 촬영 장면과 표시 오브젝트를 숨기고 충돌 삼각형을 청록색 선으로 표시한다. Three.js는 보행 BVH가 사용하는 변환 완료 메시를 그대로 표시한다. PlayCanvas는 물리에 연결한 GLB의 렌더 메시를 같은 변환으로 표시한다. 시점을 유지한 채 `촬영 장면 보기`로 돌아올 수 있다. 이 표시는 시각 비교를 위한 것으로 물리 계산을 바꾸지 않는다.
- `위치 JSON 저장`: 앱 이름, 월드/레이어, 릴리스, 창 크기, 발·눈 위치, 시선, 속도, 보행 설정, 실제 적용 경사 제한, 자산 해시와 변환을 저장한다. 파일 이름은 `three-location-시간.json` 또는 `playcanvas-location-시간.json`이다.
- 비교 경로 재생과 시대 전환을 시작하면 충돌 면 표시를 끈다. 재생 중에는 위치 기록과 충돌 표시 버튼이 비활성화된다. 성능 측정은 새로고침한 뒤 충돌 표시를 사용하기 전에 진행한다. 표시를 한 번 켜면 진단 렌더 자원이 메모리에 남는다.

문제 위치에서 촬영 화면과 충돌 화면을 각각 캡처하고 JSON을 함께 남긴다. 벤치 뒤로 떨어지는 경우 넘어가기 전과 떨어진 후의 위치를 각각 기록한다. 막힌 곳에서 `R` 또는 `시작점으로`로 복귀할 수 있다.

### 사용자 관찰과 보행 구현의 차이

사용자는 건물 통과가 전반적으로 개선됐지만 다음 현상이 남았다고 보고했다.

1. 현관 창문 아래 벽에 다른 형상이 겹쳐 보인다. 두 앱의 같은 벽에서 보이며, 벽 뒤 가구라는 해석은 아직 확인되지 않았다. 공통 SOG 데이터, 시점과 벽 정합을 조사해야 한다. 충돌 메시를 표시한다고 Splat 불투명도가 수정되지는 않는다.
2. 현관 벤치를 넘어가면 약간 아래로 떨어지고 되돌아오지 못한다. 두 앱의 같은 구간에서 발생한다. 충돌 표면의 높이 차이·빈 부분과 보행 처리를 위치 기록으로 확인해야 한다. 원인과 수정 여부는 아직 확정하지 않았다.
3. 앞 계단을 올라가는 경로가 앱마다 다르다. 같은 GLB를 읽지만 보행 처리가 같지 않다.

| 보행 처리 | Three.js | PlayCanvas |
|---|---|---|
| 충돌 표면 | 공통 GLB를 월드 좌표로 구워 만든 BVH | 공통 GLB로 만든 Ammo 정적 메시 |
| 플레이어 | 직접 구현한 캡슐 침투 해소·속도 보정 | 질량 75의 동적 캡슐, 마찰 0.8 |
| `maxSlopeDeg: 35` | 가파른 위쪽 접촉을 수평 벽으로 처리 | 설정을 적용하지 않음 |
| 일정 높이의 계단을 자동으로 넘는 처리 | 최대 20cm, 앞쪽 착지 면과 캡슐 이동 공간 확인 | 없음 |
| 입력 없이 서 있을 때 | 지지가 유지되면 위치와 속도를 고정 | 동적 캡슐의 중력·접촉·마찰 계산 유지 |
| 복귀 | 미해결 침투·시작 높이보다 10 m 아래면 최근 지지 위치로 복귀, 수동 R | 수동 R |

현재 계단 반응을 엔진 자체의 보행 성능 차이로 판정하면 안 된다. 공통 캡슐 크기와 이동 속도만 맞춘 상태다. 실제 탐방 보행을 평가하려면 계단 높이, 경사 제한, 지면 추종, 작은 낙차와 막힌 구간의 복귀 정책을 정하고 양쪽 구현에서 적용해야 한다. 이번 진단 기능 추가에서는 보행 처리와 충돌 자산을 변경하지 않았다.

## 데이터와 연결 방식

| 항목 | 기존 Knock Hall | 추가 Sunnyvale |
|---|---|---|
| Gaussian 수 | 900,000 | 3,999,361 |
| SOG 처리 | 축소 후 SH 0으로 변환 | 배포 SOG 그대로 사용, 포함된 SH 유지 |
| 충돌 메시 | 수동 상자 프록시 24삼각형 | 장면과 함께 배포된 메시 337,680삼각형 |
| 장면 기능 | 보행, 정보, 현재·과거, 비교 경로 | 보행과 벽 근접 확인 |

추가 장면은 더 크고 시선에 따른 색 표현 데이터도 다르다. 기존 장면과의 FPS 차이를 엔진 성능 차이로 해석하지 않는다. 기존 측정 결과에 새 장면 결과를 섞지 않는다. Sunnyvale에는 실제 과거 자료나 장소 설명을 추가하지 않았으며 과거 버튼과 경로 재생 버튼을 표시하지 않는다.

**SOG에만 Z축 180° 회전**을 적용하고 충돌 GLB는 회전 없이 사용한다. 기존 장면의 X축 회전과 별도로 `shared/public/world/sunnyvale.json`에 기록했다. 시작 발 위치는 `[0, 0.17, 0]`, 눈높이는 1.6이다. 회전하지 않은 충돌 메시의 시작점 지면 높이는 약 0.107이다. 단위는 공식 예제의 사용 방식을 따르며 실측 축척을 검증한 것은 아니다.

### 건물 통과 오류 수정

최초 설정은 공식 예제의 공통 부모 회전 설정을 따라 두 파일에 같은 Z축 180° 회전을 적용했다. 사용자가 두 앱에서 시작점 왼쪽 건물을 통과한다고 보고한 뒤, 실제 다운로드한 파일을 대조했다. SOG 좌표를 디코딩해 회전한 점들과 GLB의 원래 정점을 투영해 비교하면 건물 외곽이 같은 방향에 놓인다. GLB 자체는 이미 Y-up이며 정점 Y 범위는 약 -1.825–26.377이다. GLB를 다시 뒤집으면 건물 대부분이 지면 아래로 이동한다. 두 파일의 회전을 같게 해야 한다는 전제가 잘못됐다.

기존 접지 테스트는 뒤집힌 메시의 일부 표면에도 접지할 수 있어 이 오류를 잡지 못했다. 실제 설정의 변환을 읽도록 테스트를 수정하고 왼쪽 건물 벽의 시선 차단·보행 차단 검증을 추가했다. 기존 회전에서는 새 벽 테스트가 실패했고, 충돌 메시의 회전을 제거한 뒤 통과했다. 벽 확인 구간은 `z=-12`, `x=-8`에서 왼쪽으로 접근하는 경로다. 눈높이 1의 광선은 벽의 `x≈-10.50`에서 교차하고, 보행 캡슐은 `x≈-10.27`에서 멈춘다. 이는 제공된 메시의 해당 벽을 검증한 결과이며 모든 벽의 촬영 데이터 정합을 보장하지 않는다.

충돌 GLB의 Draco 압축은 다운로드 후 한 번 해제했다. 정점 위치와 삼각형을 보존하고 런타임에서는 두 앱이 같은 일반 GLB를 읽는다. 추가적인 메시 단순화는 하지 않았다. 제공된 메시가 모든 촬영 벽에 정확히 맞는지는 화면에서 확인해야 한다. 충돌 메시의 삼각형 수가 많다고 Splat 벽의 불투명도가 보장되는 것은 아니다.

### 계단 걸림과 정지 중 미끄러짐 수정

사용자가 저장한 네 위치로 실제 Sunnyvale 충돌 메시에서 재현했다. 단위는 m이며 좌표는 발 위치다.

| 위치 기록 | 발 위치 (x, y, z) | 사용자 관찰 |
|---|---|---|
| `three-location-1790927201617.json` | (-10.21335, 0.03604, -14.29915) | 앞 계단에서 걸림 |
| `three-location-1790927263156.json` | (-10.94912, 0.39106, -14.17821) | 좌우로 움직이면 일부 올라감 |
| `three-location-1790927340840.json` | (-13.66356, 0.53731, -21.88231) | 정지 중 천천히 미끄러짐 |
| `three-location-1790927372749.json` | (-13.59994, -0.21628, -22.25220) | 이후 아래로 떨어짐 |

수정 전에는 세 번째 위치에서 입력 없이 40초를 계산하면 네 번째 위치 근처까지 미끄러지고 약 75cm 내려갔다. 경사진 삼각형에 매 프레임 중력을 적용하고 침투를 해소하면서 수평 이동도 생겼다. Three.js 보행기는 입력이 없고 아래의 지지가 확인되는 경우 위치와 속도를 유지하도록 수정했다. 지지가 없으면 계속 낙하하며 기존 낙하 복귀 테스트도 유지한다.

앞 계단에는 약 49°의 짧은 면이 있어 35° 경사 제한으로 정면 접근이 막혔다. Three.js에 최대 20cm 턱 오르기를 추가했다. 막힌 이동에서만 시도하며, 앞쪽의 걸을 수 있는 면, 상승·전진 공간, 착지 후 충돌과 실제 이동을 확인한다. 연속 급경사, 높은 턱과 낮은 천장은 계속 차단한다.

실제 네 위치에서 40초 정지 후 이동량 2mm 미만을 확인했다. 첫 계단 위치에서 좌우 조작 없이 정면으로 1초 이동하면 60fps와 20fps 모두 현관 바닥 높이(약 0.57m)에 도달했다. 15cm 턱 통과, 30cm 턱 차단, 낮은 천장 차단과 기존 벽·급경사·낙하 복귀를 포함한 Three.js 테스트 12개가 통과했다. 브라우저에서의 이동감 확인은 별도로 필요하다.

이번 수정은 Three.js 보행기에 적용했다. PlayCanvas의 동적 캡슐과 보행 방식은 여전히 다르므로 계단 경로·정지 동작 차이만으로 엔진 품질을 비교할 수 없다. 벤치를 넘은 모든 경로의 복귀와 벽 비침까지 해결했다는 의미는 아니다.

### 창문 아래 벽 비침 조사

사용자의 `playcanvas-location-1790928086895.json`과 촬영 화면·충돌 선 화면 두 장을 대조했다. 발 위치는 `[-14.24447, 0.55009, -11.09019]`, 눈 위치는 `[-14.24447, 2.15009, -11.09019]`다. 사용자는 Three.js에서도 같은 위치에 같은 형상이 겹쳐 보인다고 확인했다. 형상이 벽 뒤 가구인지는 아직 확인되지 않았다.

저장된 카메라 위치·방향·화면 비율과 앱의 70° 시야각으로 빨간 박스 영역에 CPU BVH 광선 225개를 검사했다. 박스 경계는 캡처에서 추정했으며 실제 브라우저 픽셀 검사는 아니다. 모든 표본에서 충돌 면을 만났고 거리는 약 2.16~6.90m였다. 카메라의 near clip은 0.05m이므로 이 시점의 증상을 근접 클리핑만으로 설명하기 어렵다. 이 결과가 모든 표본의 충돌 면이 촬영 화면의 벽과 정확히 일치한다거나 영역 전체에 구멍이 없음을 보장하지는 않는다. 검사 결과는 `artifacts/browser-test-2026-10-02/sunnyvale-wall-ray-check.json`에 기록했다.

두 앱의 일반 화면에는 SOG만 표시하고 충돌 GLB를 불투명한 벽으로 그리지 않는다. 따라서 충돌 면은 이동을 막지만 SOG 뒤 형상을 가리는 렌더링 면은 아니다. 충돌 선 화면도 뒤쪽 선까지 표시하므로 비침 여부를 직접 판정할 수 없다.

설치된 렌더러 소스에서 PlayCanvas GSplat의 기본 설정은 premultiplied alpha blending과 `depthWrite: false`, Spark도 기본적으로 투명도·premultiplied alpha를 사용하고 `depthWrite: false`임을 확인했다. 이는 Gaussian 합성을 위한 설정이며 해당 값 자체를 오류로 판정하지 않는다. 앱에는 벽 불투명도를 별도로 낮추는 설정이 없다.

현재 우선 조사 대상은 공통 SOG에 남은 불필요한 Gaussian 형상이나 벽의 부족한 불투명도·재구성 품질이다. 양쪽의 같은 위치에서 보인다는 사용자 관찰과 일치하지만 원인 확정은 아니다. 충돌 메시 수정이나 카메라 near clip 변경으로 이 증상이 해결됐다고 보고하지 않는다.

다음 확인은 동일 시점에서 원본 SOG의 해당 벽과 겹친 Gaussian을 구분하는 것이다. 불필요한 형상이 확인되면 자산을 편집한 별도 버전으로 양쪽에 동일하게 적용해 비교한다. 불투명한 차폐 메시가 필요하다면 실제 벽에 맞춘 메시와 창문·출입구 처리가 필요하다. 현재 충돌 메시 전체를 그대로 불투명하게 그리거나 `depthWrite`만 켜는 변경은 적용하지 않았다. 벽 비침은 아직 해결되지 않았다.

## 재현

저장소 루트에서 의존성을 설치한 뒤 실행한다. 변환 스크립트는 이 예제의 단일 충돌 메시를 위한 것이다.

```bash
curl --fail --location https://code.playcanvas.com/examples_data/example_sunnyvale/sunnyvale.sog --output shared/public/assets/sunnyvale.sog
curl --fail --location https://code.playcanvas.com/examples_data/example_sunnyvale/sunnyvale.glb --output /private/tmp/atlas-sunnyvale-compressed.glb
node scripts/decode-collision.mjs /private/tmp/atlas-sunnyvale-compressed.glb shared/public/assets/sunnyvale-collision.glb
rm /private/tmp/atlas-sunnyvale-compressed.glb
python3 scripts/update-asset-manifest.py
pnpm check
```

원격 파일이 교체되면 위 해시와 달라질 수 있다. 그 경우 새 자료로 구분해 기록한다.

## 검증 결과와 남은 확인

`pnpm check`가 통과했다. 자산 크기·해시, 공용 데이터, 장면 선택, Three.js의 새 메시 로드·접지·왼쪽 벽 차단 테스트, 타입 검사, 두 앱의 프로덕션 빌드와 릴리스 산출물 검사를 포함한다. 5173·5174의 새 장면 JSON 응답도 HTTP 200으로 확인했다.

PlayCanvas 앱에 포함된 Ammo WASM도 Node에서 같은 충돌 메시와 캡슐 크기·질량·마찰로 별도 검증했다. 같은 벽으로 5초간 이동 입력을 주었을 때 발 위치 `x≈-10.25`, `y≈-0.073`, `z≈-11.99`에서 막혔다. 이는 물리 엔진의 해당 벽 차단 검증이며 PlayCanvas 앱의 브라우저 실행 검증은 아니다.

실제 브라우저에서의 벽 비침, PlayCanvas의 새 메시 보행, 시각 정합과 반응 속도는 사용자 확인이 남아 있다. 자동 테스트 통과가 화면 품질을 보장하지 않는다.

새 장면에서 문제가 줄어들면 기존 촬영 데이터나 수동 충돌 프록시를 먼저 조사할 근거가 생긴다. 두 장면에서 계속 보이면 충돌 정합, 카메라 거리·클리핑, Splat 렌더러 설정을 함께 조사한다. 어느 결과도 단독으로 원인을 확정하지는 않는다.
