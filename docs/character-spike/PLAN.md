# 캐릭터·만남 스파이크 계획

- 작성·갱신일: 2026-11-07
- 상태: 1–3회차 이동·합장·안내문 구현, 4회차 소규모 다중 접속 구현·공개 배포 및 두 브라우저 기능 검증 완료. 실제 8기기·장시간 시험은 미실시. 정원 8명·인원 표시·자동 입장으로 변경(아래 변경 결정 참조).
- 운영: 이 문서에 전체 순서, 결정 변경, 회차별 결과와 다음 작업을 계속 기록한다.

## 1. 목적과 기준 구성

기술 테스트는 완료한 것으로 두고, 한 엔진·한 장면에서 다음 경험을 단계적으로 확인한다.

1. 내 아바타의 전신을 보며 3인칭으로 이동한다.
2. 교무님 NPC에게 다가가 합장 인사를 받고, 나도 인사한다.
3. 교무님이 건네는 안내문을 받아 읽는다.
4. 같은 공간에 접속한 다른 방문자를 만난다.

1회차 기준 구성은 앞서 제안한 **PlayCanvas + Ammo, `sunnyvale-content`, 현재 시대**로 잡는다. 데스크톱 조작을 중심으로 진행하며, 기존 모바일 축소 방침을 유지한다. iPhone 결과로 최종 판정을 바꾸지 않는다. 엔진 비교를 다시 시작하지 않는다.

전신 아바타와 단계적 진행은 사용자 요구다. 임시 아바타의 외형, 아래의 구체적인 키 배치, 좁은 곳의 카메라 전환 방식은 제안이며 실제 화면을 보고 조정한다. ‘내 아바타’는 우선 사용자가 조종하는 캐릭터를 뜻한다. 사용자 얼굴 재현이나 외형 편집기는 이번 범위에 넣지 않는다.

### 경험 참고: 산사

- 사용자 제공 참고 사이트: [산사, 잠깐 쉬어가요](https://sansatemple.com/) (2026-11-07 공유).
- 공개된 조작 안내에서 바닥 클릭·WASD·방향키 이동, 드래그 둘러보기, 확대·축소, 합장 입력을 확인했다. 환경음·염불·효과음의 개별 조절 안내도 있다.
- 이번 계획에서는 공간을 직접 걸으며 간단한 몸짓으로 인사하는 경험을 참고한다. 이는 사용자 요청과 사이트 안내를 연결한 해석이며, 사용자가 특히 참고한 세부 요소는 아직 특정하지 않았다.
- 사이트의 실제 3D 화면과 카메라의 벽·좁은 구간 처리, NPC 동작, 다중 사용자 동기화는 이번 텍스트 확인으로 검증하지 않았다. 해당 기능이 있다고 가정하거나 구현 방식을 추정해 채택하지 않는다.
- 현재 1–4회차 순서는 유지한다. 클릭 이동·절하기·염주·목탁 등 참고 사이트의 다른 기능을 이번 범위에 자동으로 추가하지 않는다.

## 3. 1회차 범위

- poly.pizza의 Quaternius Casual Character(CC0)를 방문자로 사용한다. 대기·걷기와 손가락 뼈대를 확인했으며, [자산 출처](ASSET-LICENSE.md)를 기록했다. 교무님 복장·합장·전달 동작은 후속 제작 대상이다.
- 기본 카메라는 아바타 뒤쪽, 조금 높은 위치에서 전신을 화면 하단 중앙에 보여준다. 수평에 가까운 시선을 피하도록 상하 회전을 제한한다. 마우스로 둘러보고 WASD로 이동하는 구성을 시험한다.
- 이번 시험 안내·조작은 한 패널로 묶고 PC·모바일 모두 닫힌 상태로 시작한다. 닫으면 버튼 하나만 남고, 열면 화면 안에서 내용만 스크롤한다.
- 대기·걷기·방향 전환을 연결하고, 발과 지면의 관계 및 기존 보행 충돌을 확인한다.
- 캐릭터 모드에서 WASD는 이동, 화살표키와 마우스 드래그는 둘러보기, R은 시작점 복귀다. 화살표 회전은 누르고 있는 시간에 비례하며 마우스와 같은 상하 제한을 적용한다.
- 기존 자동 카메라 연출은 이 회차에서 비활성화한다. 일반적인 추적 카메라와 충돌 회피 동작은 사용한다.
- 야외 이동부터 완성한 다음 벽과 좁은 구간 하나에서 카메라 정지·복귀를 시험한다.
- 이번 회차에는 NPC, 안내문, 네트워크, 아바타 커스터마이징을 포함하지 않는다.

### ‘자동 카메라 연출을 끈다’의 의미

기존 콘텐츠 연출은 특정 구역에 진입하면 **정해진 8초 경로로 카메라가 이동하고 자막을 표시한 뒤 복귀하는 장면**이다. 재생 중에는 일반 이동을 잠시 멈추고, 끝나거나 건너뛰면 원래 위치와 조작을 복구한다.

이번에 끄는 것은 이 연출이다. 아바타를 따라가는 카메라, 마우스 회전, 벽 앞에서의 위치 조정까지 끈다는 뜻이 아니다. 근거: [콘텐츠 시험 결과](../content-spike/RESULTS-01.md), [연출 제어](../../apps/spike-playcanvas/src/content-cue.ts), [연출 시작·복귀 연결](../../apps/spike-playcanvas/src/main.ts).

### 좁은 곳의 카메라: 1회차 시험안

사용자가 제안한 **카메라는 안전한 위치에 멈추고 인물만 이동하는 방식**을 시험한다.

1. 열린 공간에서는 뒤쪽에서 따라간다.
2. 좁은 구간에서는 카메라 위치를 유지하고 인물이 움직이게 한다. 필요하면 카메라 방향만 돌려 인물을 바라본다.
3. 다시 열린 공간으로 나오면 따라가는 위치로 부드럽게 복귀한다.

카메라를 완전히 고정할지, 방향은 인물을 따라 돌릴지는 별개의 선택이다. 첫 시험은 위치를 유지하고 방향은 따라가는 방식으로 한다. 작은 지정 구간에서 먼저 검증하며 모든 지형에 대한 자동 해결을 1회차의 완료 조건으로 삼지 않는다.

**한계:** 인물이 모퉁이를 돌아 벽 뒤로 들어가면 고정된 카메라에서는 보이지 않는다. 이 경우 안전한 다른 위치로 이동하거나 인물 쪽으로 거리를 줄이는 보완 동작을 시험해야 한다. 전신 표시를 기본 목표로 유지하되, 매우 좁은 곳에서도 전신·벽 비투과·고정 위치를 모두 보장한다고 약속하지 않는다. 전신이 잘리는 구간은 결과에 남기고 최종 정책을 정한다.

충돌과 가림 판단에는 장면의 충돌 형상이 필요하다. 스플랫으로 보이는 벽과 충돌 형상이 일치하는지 시험 구간에서 확인한다. PlayCanvas는 두 점 사이의 충돌 형상을 검사하는 [ray cast](https://developer.playcanvas.com/user-manual/physics/ray-casting/)를 제공하지만, 이것만으로 카메라의 화면 가장자리까지 벽을 뚫지 않는다고 보장할 수는 없다. 실제 화면에서 검증한다.

카메라가 멈추거나 복귀할 때 이동 방향이 갑자기 뒤집히지 않는지도 확인한다. 카메라가 아바타와 떨어진 위치에 있으므로 그 시점에 필요한 배경이 표시되는지도 함께 본다.

### 1회차 확인 항목

| 상황 | 확인할 동작 |
|---|---|
| 열린 공간 | 정지·걷기·방향 전환 중 머리부터 발까지 보이고, 아바타가 지면 아래로 빠지지 않는다 |
| 벽 근처에서 이동·카메라 회전 | 인물이 벽을 통과하지 않고, 카메라가 벽 안으로 들어가 배경 뒤편을 노출하지 않는다 |
| 좁은 구간 진입·이탈 | 카메라를 멈춘 채 인물이 이동하고, 빠져나오면 추적이 복구된다 |
| 모퉁이에서 가림 발생 | 고정 카메라의 한계를 재현하고, 보완 동작으로 다시 인물을 볼 수 있는지 확인한다 |
| 카메라 동작 전환 | 입력 방향이 갑자기 뒤집히거나 카메라 위치가 순간적으로 튀지 않는다 |

구간과 실행 조건, 성공·실패 및 남은 제한을 기록하고 실제 조작 화면으로 사용자에게 확인받는다. 아직 구현하지 않은 동작이나 시험하지 않은 구간을 완료로 표시하지 않는다.

## 4. 후속 회차의 경계

**2회차:** 교무님은 우선 한 자리에 머문다. 접근 시 사용자를 바라보고 합장 인사하며, 사용자는 별도 키로 답한다. `G`는 임시 제안이다. 인사 중 이동 처리와 재인사 간격을 정하고 복장·손 모양·자세를 확인한다. 자유 대화와 배회는 포함하지 않는다.

**3회차:** 사용자 제안에 따라 NPC 옆 책상에서 안내문을 집어 이용자에게 건넨다. 가까이에서 NPC 인사가 끝난 뒤 멈춰 `E` 또는 받기 버튼을 누른다. 전달 후 ‘안내문 열기’ 버튼이 생기고, 전체 화면에서 읽고 닫거나 다시 연다. 전달·읽기 중 이동은 잠시 막는다. 중복 입력·중단 후 재시도·닫은 뒤 이동을 확인한다. 안내문 문안은 시험용이며 실제 교리 해설이 아니다. 소지는 현재 실행 중만 유지하고 `R`·새로고침으로 초기화한다. 종이 물리·영구 보관함은 포함하지 않는다.

**4회차:** 서로 다른 기기의 방문자를 실시간으로 보려면 위치와 행동을 중계할 서버 또는 관리형 실시간 서비스가 필요하다. 1–3회차는 다중 사용자 동기화 서버 없이 진행한다. 4회차에서 소규모 입장·퇴장·위치·방향·걷기·인사만 연결하고, 계정·채팅·영구 보관함은 제외한다. 여러 명이 같은 NPC에게 인사하거나 안내문을 받을 때의 처리 방식은 이 회차 전에 결정한다.

### 공유 페이지와 다중 접속의 다음 단계 (2026-11-07)

공유 사이트의 첫 화면은 현재 캐릭터·인사·안내문 체험의 입장, 순서, 조작 안내를 우선 배치한다. 기존 엔진 비교·측정 보고서는 아래 접힌 영역에 보존한다. 생성 원본은 `scripts/build-report-site.py`이며 현재 체험의 진입 주소는 `tests/playcanvas/?scene=content&character=1`이다. 이 변경은 로컬 배포 산출물 준비이며 공개 사이트 반영과 구분한다.

GitHub Pages는 화면·3D 자산 배포에 계속 사용할 수 있다. 4회차에는 별도 실시간 서버 또는 관리형 서비스를 연결해 두 브라우저에서 입장·퇴장·위치·방향·걷기·합장이 서로 보이는 것부터 확인하는 방향을 제안한다. NPC와 안내문은 우선 각 방문자가 독립적으로 이용하는 안이며, 공유 방식과 서비스 선택은 아직 확정하지 않았다. 이 제안 시점의 빌드에는 다중 접속 기능이 없었다. 이후 실행 결정은 아래 4회차 결정·실행에 기록한다.

### 4회차 실행 제안: 작은 다중 접속부터 (2026-11-07)

현재 공유 페이지와 1–3회차 빌드를 먼저 배포해 기준 버전을 남긴다. 이후 같은 엔진·장면에서 다음 순서로 구현한다. 아래 인일은 구현·기능 확인에 대한 추정이며 호스팅 가입·사용자 확인 대기 시간은 포함하지 않는다. 아직 다중 접속 구현이나 서버 배포를 수행한 상태는 아니다.

| 단계 | 작업 | 완료 기준 | 작업량 추정 |
|---|---|---|---|

이번 제안은 위치·동작을 중계하는 소규모 체험이다. 내 이동과 지형 충돌은 기존 클라이언트에서 처리하고 다른 방문자는 서로 밀거나 길을 막지 않는다. NPC·안내문은 각자 독립적으로 이용하며, 다른 방문자의 안내문 수령 동작·소지 상태는 이번 공유 범위에 포함하지 않는다. 인물 구분은 임시 번호·색으로 시작하고, 계정·채팅·음성·아바타 선택은 후속 요청으로 남긴다. 공개 서버 연결이 없어도 기존 단독 체험은 사용할 수 있게 한다.

## 4회차 결정·실행 — 2026-11-07

사용자가 기존 VPS 이용과 배포를 승인했다. GitHub Pages의 정적 앱을 유지하고 `atlas-ws.summerz.net`의 별도 Docker 중계 서버에 연결한다. 최대 4명, 초당 10회 위치·방향·걷기·달리기·합장을 공유한다. 기본은 단독 탐색이며 ‘안내·조작’에서 검토용 비밀번호로 함께 입장한다.

NPC 인사와 안내문 전달·소지는 각 방문자의 로컬 상태로 유지한다. 다른 방문자끼리 충돌하지 않으며 계정·채팅·영구 저장·공유 NPC 순서는 포함하지 않는다. 서버가 중단돼도 단독 탐색을 유지하고 자동 재접속한다. 재입장은 새 임시 ID를 받는다.

[4회차 결과·검증 범위](RESULTS-04-MULTIPLAYER.md)에 실제 검사와 배포 결과를 기록한다. 위 후속 회차 제안은 당시 계획이며, 현재 구현 범위는 이 결정과 결과 기록을 따른다.


## 인원 표시와 자동 입장 변경 — 2026-11-07

사용자 요청에 따라 정원을 8명으로 변경한다. 첫 화면의 ‘입장하기 N/8’은 서버의 실시간 인원을 표시하고, 만석이거나 인원을 확인할 수 없으면 비활성화한다. 버튼을 누르면 기존 공간에 자동 연결하며 패널의 별도 입장·비밀번호·단독 전환 조작은 제거한다. NPC·안내문은 기존처럼 각자 이용한다.

정상 페이지 이동·탭 닫기 시 즉시 자리를 해제하고 첫 화면의 숫자를 갱신한다. 네트워크 단절·강제 종료는 서버 감지까지 최대 약 40초 지연될 수 있다. 동시에 눌러 자리가 부족해진 경우 서버가 9번째 입장을 거절하고 입장 화면으로 돌아갈 수 있게 한다. 8명 제한과 8기기 성능 검증은 구분한다. 변경 전 4명·수동 입장 기록은 당시 결정으로 보존한다.
