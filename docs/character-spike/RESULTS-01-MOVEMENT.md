# 1회차 보완: 인물 크기·낮은 턱·장면 유지

- 날짜: 2026-11-07
- 범위: PlayCanvas + Ammo, `?scene=content&character=1`.
- 요청: 집·벤치 대비 인물 확대, 달리기 1.8배, 낮은 지붕 집 부근의 작은 단차에서 탈출, 더 이른 로딩, 뒤돌아봐도 이미 불러온 장면 유지.

## 적용

| 항목 | 변경 |
|---|---|
| 인물 크기 | 모델과 물리 캡슐을 함께 12% 확대. 높이 1.7 → 1.904, 반지름 0.25 → 0.28 단위. 맵은 그대로 유지 |
| 달리기 | 걷기 2, 달리기 3.6 단위/초로 1.8배. 기존 Shift·터치 입력 사용 |
| 낮은 턱 | 이동이 막히고 지면에 지지된 경우 최대 0.2 단위 높이의 걸을 수 있는 윗면으로 보조 이동. 전체 캡슐의 위·앞·아래 충돌 검사로 벽·낮은 천장을 확인 |
| 미리 로딩 | 구역 경계까지 2 → 12 단위. 카메라 방향 예측이 아니라 인물 주변 X/Z 거리 기준으로 적용 |
| 이미 본 구역 | 캐릭터 모드에서는 거리로 해제하지 않고 현재 장면 종료·전환까지 유지. 불러오는 중 멀어진 구역도 완성 후 유지 |
| 상주 예산 | 최대 2 → 6개 정밀 구역. 현재 선택된 자산의 정밀·원거리 점 수를 합산해 예산을 함께 확대. 전체 장면을 담지 못하는 유지 설정은 명시적으로 거부 |

이전 [달리기 기록](RESULTS-01-RUNNING.md)의 1.7배·크기 미변경은 당시 결과다. 이번 설정이 이를 대체한다. 크기 확대는 시각적 비율 조정이며 실측 축척 보정이 아니다. 0.2 단위도 실물 20cm라고 검증한 값은 아니다.

구현: [이동 통합](../../apps/spike-playcanvas/src/main.ts), [턱 보조](../../apps/spike-playcanvas/src/character-step.ts), [캐릭터 로딩 예산](../../apps/spike-playcanvas/src/character-streaming.ts), [스트리머](../../shared/src/streaming.ts). 거리 해제를 사용하던 기존 기술 비교 모드는 기본 동작을 유지한다.

## 검증

별도 headed Playwright CLI `steps`, 시험 탭 1개, Apple M4 Pro / ANGLE Metal. 데스크톱 1440×900과 모바일 크기 390×844, DPR 1. 개발 서버 기능 시험이며 iPhone 실기기·장시간 성능 측정은 아니다.

브라우저 좌표 주입은 스트리밍 수명 확인이며 해당 경로의 실제 보행 성공을 뜻하지 않는다. 첫 스트리밍 확인 스크립트는 chunk ID와 entity ID를 혼동해 실패했다. 실제 엔티티의 `-detail` 접미사로 수정한 뒤 새로 로드하여 다시 검증했다. 실패 출력도 보존한다.

`pnpm check` 통과: 스크립트 19개, 공통 35개, Three.js 27개, PlayCanvas 21개 시험과 타입 검사·두 앱 빌드·자산 검증. 로컬 빌드 `local-c5b967dd2a7e-804d3d640af4`, 배포하지 않았다. 번들 크기 경고는 남아 있다. 브라우저 콘솔 오류는 favicon 404였다. 주요 검증 뒤 시험 브라우저를 닫았다. 이후 위치 보고 버튼 확인을 위해 다시 연 단일 시험 탭은 사용자가 직접 막힌 위치로 이동하겠다고 요청하여 열어 두었다. 사용자 Chrome과 기존 개발 서버는 유지했다.

## 막힌 위치 전달

사용자가 정확한 위치를 전달할 수 있도록 기존 **위치 JSON 저장** 버튼을 **안내·조작** 패널 안에 노출했다. 파일에는 발 좌표·카메라 위치/방향·속도·충돌체·스트리밍 상태가 들어간다. 버튼 표시와 기존 저장 핸들러 연결을 확인했으며 이번 보완에서 다운로드 자체는 재시험하지 않았다. 패널을 닫으면 안내·조작 버튼 하나만 남는다.

사용자가 시험 브라우저에서 직접 이동한 뒤 “여기예요”라고 알려 주어 아래 위치를 확보하고 재현했다.

## 사용자 신고 지점 재현·보정

사용자가 확정한 발 좌표는 **(24.2026, −0.1130, 32.9541)**이다. 정밀 구역 1–5가 준비됐고 스트리밍 진입 차단은 0회였다. 같은 자리에서 네 방향으로 각각 1.5초 입력했으나 최대 약 0.35 단위 이동에 그쳤다. 수직 충돌 레이 조사에서 이 홈의 바닥은 약 y=−0.12~0.04, 주변은 약 0.5~0.75였다. 기존 0.2 단위 턱 보조로 넘을 수 없는 좁고 깊은 충돌 홈이었다. 수치는 장면 좌표 단위이며 실물 길이가 아니다.

현재 캐릭터 야외 장면에만 **x=23.7~24.95, z=32.5~33.65, 윗면 y=0.6**인 보이지 않는 정적 박스 바닥을 추가했다. 바닥 아래는 y=−0.2이며 주변 벽 충돌은 유지한다. 공유 원본 메시·기술 비교 장면·cameraLab에는 적용하지 않는다. 전역 턱 높이는 0.2로 유지한다. 이 위치의 보행 표면을 정리한 것이며 다른 홈을 자동 감지하는 기능은 아니다.

## 이동 보완 종료 (사용자 요청)

두 번째 신고 발 좌표는 `(20.4595, −0.0191, 34.4195)`였다. 바닥 지지는 있으나 주변 높이 차이로 방향에 따라 이동이 막혔다. 이 지점에도 국소 박스 바닥을 추가했다: x=19.25~21.3, z=33.35~35.35, 윗면 y=0.45. 북·서·북서·북동 방향의 걷기/달리기 왕복과 이어지는 북쪽 탈출을 8회 확인했다. 전체 맵의 결함 해결을 뜻하지 않는다.

사용자가 바닥 높이를 올리는 대안을 제안한 뒤, 이를 턱 허용 높이 조정으로 해석해 두 보정 박스를 **런타임에서만 비활성화**하고 0.4/0.6/0.8 높이 보조를 기존 0.2 보조에 추가해 두 좌표의 W/A 이동을 탐색했다. 첫 좌표는 세 높이 모두 탈출하지 못했다. 두 번째는 A 방향만 탈출했다. 이는 대안 탐색이며 최종 설정 검증은 아니다. 전역 바닥 오프셋을 추가하는 방안 자체는 구현·시험하지 않았다.

사용자의 “어느 정도 끝내고 다음으로” 요청에 따라 충돌 알고리즘 확대를 중단한다. **현재 구현은 최대 턱 0.2와 두 지점의 임시 바닥 보정을 유지**한다. 일반 지형 복구는 미해결로 남기고 NPC 인사 시험으로 이동한다. 앞서 보정면을 빼고 시험하겠다고 한 내용은 런타임 비교까지만 수행했으며, 실패한 대안으로 소스를 교체하지 않았다. 막히면 R로 시작점 복귀가 가능하다.

## 비용과 남은 한계

- 하늘 분리 자산을 사용하는 실제 페이지에서 시작 시 정밀+원거리 644,784점, 전 구역 방문 후 926,250점이 상주했다. 점 개수는 물리 RAM·VRAM 사용량이 아니다. 더 일찍 로딩하고 방문 구역을 유지하는 만큼 초기 준비 작업·렌더링·메모리 부담이 증가하며, 이번에는 모바일 성능을 재측정하지 않았다.
- 12단위 선로딩은 다운로드 완료 시간을 보장하지 않는다. 아직 준비되지 않은 충돌 구역은 기존대로 진입을 막는다. 원거리와 정밀 표현의 전환 자체는 남으며, 이번 변경은 전환을 앞당기고 이미 본 정밀 구역을 유지하는 것이다.
- 유지 정책은 현재 6구역 장면의 캐릭터 스파이크를 위한 선택이다. 장면을 종료하거나 전환할 때는 자원을 해제한다. 앱을 새로 열면 다시 준비한다.
- 턱 보조는 일반 점프·등반 기능이 아니다. 실제 지형 전체의 함정이 해결됐다는 판정은 하지 않는다. 기존 모퉁이 카메라 급전환·근접 전신 잘림도 남아 있다.
