# 콘텐츠 스파이크 계획 (최종 합의안)

- 확정일: 2026-10-14
- 합의 주체: Claude Fable 5.1, Codex GPT-6-Astra high. 토론 과정은 [README.md](README.md)와 00~05 문서에 있다.
- 초안 [00-initial.md](00-initial.md)와의 차이: 이 단계를 "경험 검증"에서 "표현 수단의 기술 시험"으로 재정의했다. 네 축은 유지하되 범위를 줄였고, 측정 전에 고정하는 합격선과 중단 규칙을 추가했다.

## 1. 이 단계의 정의

**콘텐츠 스파이크**: 대역 공개 장면 위에서 네 가지 표현 수단의 실현 가능성, 비용, 기기 예산, 데이터 계약을 확인하는 기술 시험. 십상 이해나 학습 효과를 검증하는 단계가 아니다. 그 평가는 실제 성지 데이터와 검수된 콘텐츠가 준비된 다음 단계에서 과제·비교 조건·표본을 다시 설계한다. [01-codex-critique.md](01-codex-critique.md) 질문 5의 평가 설계를 출발점으로 쓰되, 거기 적힌 8명을 확정 기준으로 승계하지 않는다.

## 2. 전제

- **대역**: `sunnyvale-era` 변형 한 가지. 원본 `sunnyvale.sog` 해시(SHA-256 `604ede4a…`)는 출처 식별용이다. 실행에 사용하는 `sunnyvale-era`의 분할·LOD·충돌 및 추가 자산 해시와 빌드 식별자를 함께 고정한다.
- **하늘 축의 대역을 Sunnyvale로 두는 근거**: 원본 iPhone 캡처([ios-playcanvas-sunnyvale.png](../implementation/measurements/2026-10-02/ios-playcanvas-sunnyvale.png))와 `sunnyvale-era` 데스크톱 캡처에 하늘 표현이 보이고, 앱에 별도 하늘 배경 설정이 없다. 제거 가능한 점 집합과 경계 보존은 미확인이며 이 시험에서 확인한다. Knock Hall 축소본은 하늘이 검게 비어 있어 하늘 축 대역이 될 수 없다.
- **두 번째 장면**: 기존 Knock Hall 변형. 실내이므로 하늘 분리의 이전은 검증하지 못하며 그렇게 기록한다.
- **엔진**: PlayCanvas + Ammo 한 구성. 스파이크 보고서의 우선 후보를 일정 가정으로 쓴 것이며 최종 선택이 아니다.
- **콘텐츠 데이터**: 실제 십상 사실 3개와 출처를 대본으로 준비해 얹는다. 학습 증명이 아니라 텍스트·음성·자막·출처·표현 구분이 같은 내용을 전달하는지 확인하는 시험 데이터다. 화면에 "기술 시험용 대역" 표시를 상시 띄운다. `sunnyvale-era`의 과거는 실제 역사 복원이 아니다.
- **제외**: 안개·강수·주야간, 동행 캐릭터·길 찾기·대화, 타임랩스, 과거 창 셰이더, 다중 컷 연출, 초심자 평가, 새 촬영, 새 공개 장면 탐색(하늘 축 실패 시에만 상한 내 조사).

## 4. 공통 작업

| 작업 | 산출물 | 추정 인일 |
|---|---|---:|
| 사실·표현 검수 | 사실 3개·출처·해설문·대역·상징 표시. 교무/해설자 1인의 역할은 정확성·표현 적절성 검수로 한정. 출처 없는 실제 인물의 대사는 만들지 않고 중립 해설문 사용 | 1–2 |
| 최소 공통 계약·계측 | 축 플래그(off = 자산 미로딩·재생 중지·자원 해제), `world.ts` 계약 최소 확장과 참조 검증, 상태 소유권 규칙(`syncInput` 확장), 작업시간·자산·실행 조건 기록 양식 | 1–2 |
| 결합·기기·실패 검증 | 6개 구성(모두 off, 축 단독 4, 모두 on) × 데스크톱/iPhone × 3회, 실행 순서 교차. 기기별 동일 경로·빌드·자산·viewport·캐시 조건. 전체 프레임 간격과 물리 시간, 메인/worker heap과 backing storage 분리 기록. 켜고 끈 직후 heap을 cold 실행과 비교하지 않음. 결합 구성만 실패하면 하나씩 빼서 좁힘. 축 보류 시 통과한 축의 결합 구성으로 줄임 | 2–3 |
| 두 번째 장면 이전·결과 정리 | Knock Hall 변형에 데이터 재배치, 사실 문장 1개 변경. 축별 코드 diff·데이터 변경·자산 재저작·실제 인시 분리 기록. 축별 통과/실패 후 대체/보류/미시험 보고 | 1–2 |

**총계: 정지 인물 기준 11–20인일 (추정). 왕복 포함 12–22. 새 공개 장면이 필요해지면 +3.5–7.**

예산 조건:

- 1인일은 8시간 실작업. 승인·섭외·기계 처리 대기는 별도. 실측 견적이 아니라 첫 회차 기록으로 갱신할 계획 범위다.
- 이용 조건이 확인된 간단한 음원·인물 자산, 자료·검수자 확보를 전제로 하며 새 고품질 모델 제작은 제외한다.
- 축별 비용은 구현·단독 시험, 공통비는 횡단 작업으로 중복 계산하지 않는다.
- 새 장면 +3.5–7인일은 조사 0.5–1과 정합·충돌·기준 시험 3–6이며 복잡한 하늘 제거 비용은 제외한다. 상한을 승인받지 못하면 해당 축을 보류한다.
- 촬영 제약 전달은 이번 범위지만 후속 촬영 체크리스트 협의 0.5–1인일은 별도다.

## 5. 성능 합격선 (잠정, 측정 전 확정)

- 활성 탐색의 전체 프레임 간격 p95 ≤ 50ms (iPhone, 고정 빌드·자산·viewport·캐시 조건).
- 동일 조건의 기준 실행 대비 전체 프레임 간격 p95 증가량 ≤ 5ms.
- 로딩, 레일 재생, 수동 탐색 통계를 분리. 3회 각각 판정.
- 이 숫자는 Codex 제안이며 기존 장면이 충족했다는 진술이 아니다. 받아들이지 않으면 대체 한도를 측정 전에 정한다. JS heap만으로 전체 메모리 안전성을 판정하지 않는다. iPhone 한 대 통과는 다른 기기 통과가 아니다.

## 6. 중단·전달 규칙

- 어느 축이든 합격선을 넘지 못하면 그 축은 보류하고 다른 축을 계속한다. 레일 실패 후 트리거+자막은 "실패 후 대체"로 기록하며 레일 축 통과가 아니다.
- 어느 축이든 촬영 전제(하늘 포함 여부, 인물 배치 공간, 연출 동선, 스카이박스용 하늘 자료)를 바꾸면 즉시 촬영 계획 체크리스트에 전달한다. 두 번째 실패를 기다리지 않는다.
- 두 번째 장면 이전에서 콘텐츠별 앱 코드 수정이 필요하면 "선언형" 주장을 철회하고 수정 범위를 기록한다.
- 하늘 교체가 성공해도 "실제 촬영 때 하늘을 빼도 된다"는 결론은 내리지 않는다. 촬영·재구성 조건은 이 저장소가 시험하지 않았다.

## 7. 실제 성지로 옮길 때 재사용 후보와 재저작

| 재사용 후보 (이전 시험으로 확인) | 재저작 (장소별) |
|---|---|
| 축 플래그, 상태 소유권, 자막·음소거·건너뛰기 경로, 기록 양식 | 스플랫·충돌 정합(기준점·단위·방향·시선 높이) |
| 스카이박스 설정 방식 | 하늘 분리 작업 자체, 수목·건물 경계 |
| 레일·트리거·구역 사전 로딩 계약 | 레일 경로, 필요 구역, 걷기 가능 구역·금지 경계·복귀점 |
| 인물 배치·표지 계약 | 인물 위치·외관·표현 승인 |
| 콘텐츠 데이터 스키마 | 사실·출처·해설문·검수 |

공통 구현비와 장소별 재저작 인시를 분리하며, 실패·미시험 축은 이전 성공으로 세지 않는다. 촬영·SfM·학습 파이프라인과 실제 역사 복원 비용은 이 단계에서 산정하지 않는다. 후속 촬영 계획에는 스카이박스용 하늘 자료 확보와 경계 재구성 입력 확보를 별도 항목으로 둔다(제안이며 검증된 촬영법이 아니다).

## 8. 실행 순서

1. 사실 3개·출처·대본, 성능 합격선, 외관 승인 예시, 고정 시점 8개, 고정 자산·빌드 확정 (공통 1–2)
2. 공통 계약·플래그·기록 양식 (공통 1–2)
3. 네 축 구현과 단독 시험 (6–11). 하늘 축은 상한에서 중단
4. 결합·기기·실패 검증 (공통 2–3)
5. 두 번째 장면 이전, 결과 정리, 촬영 계획 전달 (공통 1–2)

## 9. 초안에서 보류한 아이디어 (다음 회차 후보)

안개·강수·주야간, 동행 캐릭터, 과거를 보는 창, 타임랩스, 발자취 안내, 물건 상호작용, 조감 시점 전환, 스플랫 흩어짐 전환, 등불 남기기. 이번 네 축의 결과와 촬영 계획이 정해진 뒤 우선순위를 다시 정한다.
